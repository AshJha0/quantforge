## Quantitative analytics and trading infrastructure

QuantForge is a quantitative library written four times, in Java, C++, Python and Rust, from one set of specifications. The plan covers market data, curves, calibration, pricing, volatility, risk, portfolio analytics, hedging, market microstructure, execution analytics and systematic research. Ten stages are built and released: Foundation (stage A, v0.1), the FX and rates slices (stage B, v0.2), the equity vol slice (stage C, v0.3), curves and fixed income (stage D, v0.4), full volatility and exotics (stage E, v0.5.0), the curve layer, portfolio risk and the book (stage F, v0.6.0) rates models and xVA (stage G, v0.7.0, 2026-11-11) hedging (stage I, v0.8.0, 2026-11-12), built ahead of stage H, and research tools and portfolio construction (stage J, v0.9.0, 2026-11-17), and microstructure and execution on simulated venues (stage H, v0.10.0, 2026-11-19). Stage K, platform and release (target v1.0.0), is planned and started on 2026-11-19; nothing from it is released. Phases R1, credibility hardening (v0.4.1), and R2, risk first (v0.4.2), sit between stages D and E. See [Status](#status) below.

### What it can and cannot show
On free public data, QuantForge can show correct pricing and risk, curve quality against published curves, and signals on fitted curves tested against preregistered pass rules (research/preregs, amended 2026-11-09: one-sided deflated test, 24-trial family, Holm correction; the studies are underpowered and say so).

It cannot show tradable profitability. That needs instrument-level prices, bid and ask, financing and execution data, which cost money. This is a deliberate limit of a zero-spend project. Golden cases use synthetic inputs, except the stage J shock-library cases (`scen_j`), which carry published US Treasury par yields matched to the Federal Reserve H.15 release. Released risk covers bump-and-revalue sensitivities with P&L explain (R2); stage F adds book sensitivities with an AAD reference in Rust only, and stage G an AAD ladder for one Bermudan case (Q3b, partial; `CHANGELOG.md` 0.8.1). Stage F computes VaR, ES, backtests and parts of the FRTB standardised approach (sensitivities-based method for GIRR, FX, equity, vega and curvature) on synthetic P&L and sensitivities, which is a risk calculator, not a bank's risk system: there are no real positions and no market history behind it. **FRTB default risk charge (DRC), the residual risk add-on (RRAO) and CSR securitisations are not built**; the cross-class total (which sums classes within each scenario) was added in R6 (review finding 12, plan row R6-4, v0.8.1).

### Design principles
1. Mathematical specifications precede implementations.
2. Java, C++, Python and Rust are four equal implementations; none is the reference.
3. Each is written from the specification alone, with no shared code, FFI or generated maths.
4. Specifications, schemas, fixtures and conformance contracts are shared.
5. Expected results come from `oracle/`, never from an implementation. Agreement between implementations proves nothing on its own.
6. Correctness, numerical stability and reproducibility precede optimisation.
7. Performance claims require documented hardware, workload and methodology.

How stage H was checked, in three steps. The plain idea: no free library implements these formulas or venues, so a second lane re-derives each answer blind, from the rules and inputs alone, and a different model audits the specs and code without seeing the goldens. The formal statement: a value case counts as outside-checked only if the blind lane saw nothing that leaks the answer and every compared output matches (DR-H2); 160 of 205 value cases count (78.0%), with H-22 at 66.7%, H-23 at 71.4% and H-24 at 94.7% (`oracle/OUTSIDE_SHARES.md`). The worked example, which is also the method's limit: the blind lane reads the same rules as the first lane, so it catches arithmetic and convention slips, not a wrong rule. The multi-asset conventions carried a wrong SEC compliance date in all four builds until the SEC order was read on 2026-11-19. Dates are now per rule (HR-120): the amended tick table (Rule 612) and access-fee cap (Rule 610(c)) default to 2027-11-01, the round lot (Rule 600(b)(93)) to 2025-11-03. With no `as_of` the operations apply the amended text, which for ticks and fees is not in force before 2027-11-01; pass `as_of` for the rule in force on a date. CME 32nds are read with third digits 0, 2, 5 and 7 only; eighth-tick contracts (2-year and 3-year notes) are not supported (HR-118). All of this is self-assessment.
