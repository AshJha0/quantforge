| KR-70 | FedInvest prices | Not recorded. Read 2026-11-19: `treasurydirect.gov/robots.txt` disallows every agent but `usasearch`; the site terms allow viewing, downloading and printing "for non-commercial personal use only" and reserve reproduction and distribution to written consent; no page permits automated fetching, storage or republication. No code fetches a FedInvest page; a test pins that |
| KR-71 | Labels | Every row: "paper marks on a fitted curve; not tradable". Fills: "simulated". Pre-trade estimate: "placeholder weights". Every run prints the 11.6 sentence and the statement that the rule is plumbing evidence and that no performance claim is made. A row with another label fails verification |
| KR-72 | Source of marks | The five par yields (3 month, 2, 5, 10, 30 year) of series `recorder/us-treasury-par-yields` on branch `forward-log`, as the recorder parsed them. The job makes no market-data request. A DAY row repeats the five values for its date and the hash of the forward-log row that last set them, which is the recorder's own treatment of this public-domain series. No raw file is fetched, stored or committed |
| KR-73 | Calendar | The library calendar `USGS` through `core.calendar.is_business_day` decides which dates have rows. Early closes are full days. `tools/recorder/holidays.txt` is not used |
| KR-74 | Instruments | `UST-CM-2Y`, `-5Y`, `-10Y`, `-30Y`: each day a hypothetical semi-annual par bond (coupon = the day's par yield, maturity = date + tenor, price 100). Positions are re-struck daily into the new par bond, unit for unit, at the mark, with no cost and no fill. One unit is USD 100 face |
| KR-75 | Trading rule | Fixed rotation of eight steps (BUY 2Y, 5Y, 10Y, 30Y, then SELL the same), indexed by the count of on-time days; one IOC limit order a day at par plus or minus (half spread + 2 ticks); a BUY is for the quantity whose DV01 is USD 500, rounded down to a lot of 100 units; a SELL is for the whole position. The rule reads no market value. It is plumbing evidence; no performance claim is made from the ledger |
| KR-76 | Marks | Linear interpolation of the par yields (`core.interp.evaluate`), curve time in years of 365.25 days held inside the knots, then `bond.price.from_yield`. Yields, clean prices, accrued interest and durations are rounded half-even to 6 decimals; TCA values and curve times to 10. `mark = clean_close + accrued` |
| KR-77 | Fill simulator | `exec.sim.lit.run`, tick 1/256, lot 100, three synthetic levels a side; depth per level 20% to 50% of the reference quantity, read from `SHA-256(format, date, previous row hash, symbol)`. A rejected order never reaches the simulator |
| KR-78 | Assumed cost | Half spread 1/128 (2Y, 5Y), 1/64 (10Y), 1/32 (30Y) of a point; fees zero. Assumptions with no source |
| KR-79 | Explain | Terms: carry (coupon accrual + cash interest), roll-down, curve move, fills and costs, unexplained. Unexplained threshold exactly 0, because every term is an exact decimal and the market terms telescope; a residual is a defect (as HR-53). The identity tests bookkeeping, not a risk model, and the spec says so |
| KR-80 | Row format | `qf-paper-ledger/1`: `seq`, `ts`, `kind` (GENESIS, DAY, GAP), `label`, `format`, `body`, `prev`, `hash`; canonical bytes and hash as HR-45; one row per business day. The genesis row holds the whole configuration and its hash. Any change of configuration or fields needs a new format string, a ruling and a new ledger; rows are never rewritten |
| KR-81 | Chain and anchor | Each row holds the previous row's hash. After each push, (count, head) is stamped with OpenTimestamps on branch `paper-ledger-anchors`, as the forward log is; every anchor held must match before a push; the head is also in the commit message |
| KR-82 | On time and late | On time: the run started before 19:30:00 UTC on the next business day. Late: the curve is recorded but the cut-off has passed; the row is written with `timing` "late", the writing run's time, marks and explain, and no order. The verifier recomputes the label from `ts` |
| KR-83 | Gap and start | A business day whose cut-off has passed with no complete recorded curve gets a GAP row and is never filled in later; the next DAY row lists it and its P&L spans it. Every business day after the first has exactly one row. The first run starts at the latest on-time day; earlier days are not back-filled |
| KR-84 | Replay | Verification replays every day from the ledger alone in exact decimal, with no CLI and no outside data: opening state from the previous row, then interest, explain terms, cash, positions, NAV and P&L must equal the row exactly |
| KR-85 | Rebuild | Verification also rebuilds every DAY body through the CLI operations and compares it with the row (marks, rule, seed, book, limit check, fills, TCA) |
| KR-86 | Float allowance | In the rebuild only, decimal fields may differ by 1e-6 relative to max(1, value): binary64 `pow` may differ in the last bit between platforms. The exact replay has no allowance |
| KR-87 | Recorded trading day | A DAY row with `timing` "on_time" in a ledger that passes the full verification, anchors included. Late days and gaps do not count towards the 20 of K-2 |
| KR-88 | Limits and financing | `paper.pretrade.check` with max order 40,000 units, max notional 4,500,000, max position 40,000 units, price band 0.005, 2 orders a day, no shorts; start cash 10,000,000. Cash earns or pays the previous day's 3 month par yield, actual/365, to the cent |
| KR-89 | Guards and TCA | Every row date is checked against the prereg holdout windows by the writer and the verifier (plan 14.10 rule 6). Every order carries `exec.tca.pretrade` and `exec.tca.attribution` records (Q8k). The writer verifies the whole new ledger before replacing the file and pushes nothing that fails |
| KR-108 | Treasury yields in DAY rows (integration check, 2026-11-19, stage K coordinator lane) | Kept as values, as KR-72 says. Read at integration: the recorder's rows on `origin/forward-log` (`actions/log.jsonl`, series `recorder/us-treasury-par-yields`) publish the parsed values, not only hashes (row of sequence 346, 2026-11-18T22:13:39Z, `observations` holds the five tenors), and `docs/developer-guides/recorder-actions.md` states that rows carry the parsed values of public-domain sources only. A DAY row repeats exactly those five published values plus the source row hash, so it publishes no market data the forward log does not already publish. Precedent cited in `12-platform/paper-ledger-daily.md`. Should the recorder ever stop publishing the values (for example if the Treasury terms are read differently), the ledger must move to hashes of the inputs plus the derived marks under a new format string and ledger (KR-80) |

## Open points for the coordinator
- Library `paper.ledger.append` and `paper.ledger.verify` fix the label "crypto venue; simulated" (HR-43), so this ledger computes its HR-45 bytes and hash in the tool (a test checks them against `quantforge_core.paper.canonical`). A `label` input on those two operations would let the ledger use them; that is a four-language change and is listed in `program/STAGE_K_PAPER_HANDOVER.md`, not made here.
- The library operations used for the book legs and the limit check return the label "crypto venue; simulated" in their outputs. The job does not copy that field into the ledger.
- Whether to sign `paper-ledger` commits with the same owner key as `forward-log` (the workflow uses the secret if present) is the owner's call.
