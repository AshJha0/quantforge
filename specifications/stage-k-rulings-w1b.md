## KR-112: E1 exemption for an Integer-only operation with an `E_SCHEMA` golden (owner decision 2026-11-19, 17:44 UTC)

| # | Point | Ruling | Evidence |
|---|---|---|---|
| KR-112 | E1 gate (`tools/check_e1_coverage.py`, ruling F-2) on `risk.frtb.backtest.zone` | **Rule.** An operation on the exemption list (`conformance/E1_EXEMPT.json`) may carry a Real (JSON float) input only in goldens whose expected result is `E_SCHEMA`. A Real in any other golden (a value case, or an error case expecting `E_DOMAIN`, `E_INPUT`, `E_LIMIT` or anything else) still makes the exemption a gate problem. Every other condition of the exemption is unchanged, and nothing changes for an operation that is not on the list: it still needs a non-finite golden answered with `E_DOMAIN` (or `E_SCHEMA` under F-2a). `risk.frtb.backtest.zone` is added to the exemption list, after the planted-fault tests below passed. **Why it is not a weakening.** Before, an exemption permitted no Real input in any golden. Now it permits exactly one more case: a Real sent to an Integer field in a golden that checks it is refused as `E_SCHEMA` (here btk_k-0029, 1.5 exceptions). That golden is evidence that the operation does not accept a Real at all, which is the premise of the exemption (a non-finite value cannot reach an Integer field as a number; such a token is `E_SCHEMA`, not an integer). A Real that the operation computes with would appear in a value golden, or in an error golden expecting a later code, and is still caught. Option B (moving btk_k-0029 to four unit tests) was not taken because it would remove a cross-build check from the shared goldens. Same pattern as the stage F refinement F-2a (`stage-f-rulings.md`). | Planted faults in `python tools/check_e1_coverage.py --self-test`, all shown failing before the exemption entry was added: (a) a non-exempt operation without its NaN golden fails; (b) an exempt operation with a Real in a golden expecting `E_DOMAIN`, `E_INPUT`, `E_LIMIT` or a value fails; (c) an operation with a genuine Real input put on the exemption list fails; (d) an exempt Integer-only operation whose only Real is in an `E_SCHEMA` golden (the btk_k-0029 shape) passes. On the real tree, btk_k-0029 changed to expect `E_DOMAIN` turns the gate red. Gate after the change (measured 2026-11-19, local laptop): 336 of 368 operations with an E1 golden, 32 exempt, 0 problems. Decision record `program/STAGE_K_E1_ZONE_DECISION.md`. |

| KR-237 | One binomial algorithm for the FRTB backtest probabilities (KA-A16, KA-A17; completes KR-41 and KR-46) | `observations` keeps its range 1 to 1,000,000. **Algorithm (all four builds).** `q = 1 - p`; unnormalised weights `w_0 = 1`, `w_(k+1) = w_k * (((n - k) * p) / ((k + 1) * q))` (each operation rounded, `n - k` and `k + 1` exact); a Neumaier-compensated running sum of the weights in order k = 0, 1, ..., recording the compensated partial sum (and its scale count) at every k; when a weight exceeds `2^600`, the weight, the sum and the compensation are multiplied by `2^-600` (exact) and the scale count goes up by one; the loop stops at k = n, or after the mode `floor((n + 1) p)` once the ratio is at most 1/2 and the weight is at most `2^-64` times the partial sum (the rest then adds less than `2^-64` of the total). `P(X <= x)` is the recorded partial sum at x divided by the final sum, multiplied by `2^-600` once per scale step between them, capped at 1; it is 1 for x at or above the stopping index or at or above n, and 0 for x < 0. `amber_from` and `red_from` are the first k whose `P(X <= k)` reaches 0.95 and 0.9999. Only `+ - * /` are used, so the four builds give the same bits. **Accuracy.** Each weight carries at most about `4 k u` relative rounding and the normalisation removes the common part; against exact rational arithmetic (p = 1/100, Python `fractions`, n = 250, 1,000, 10,000, 100,000) and mpmath at 40 digits (n = 1,000,000) the largest relative error is 6.6e-15 (measured; `oracle/STAGE_K_AUDIT_A_CHECKS.json`); the old lgamma form was 1.3e-10 off at n = 100,000 and 6.6e-10 at 1,000,000, outside the class `simple_analytic` (1e-10). **p.** Both operations use the binary64 literals 0.01 and 0.025 (KA-A17: the zone operation used `1 - 0.99`, which is 0.010000000000000009). New value goldens at n = 100,000 and 1,000,000 are checked against the exact computation.
