# Stage H rulings, wave 2 engines (PR 2 lane): 2026-11-18

Written 2026-11-18 by the PR 2 preparation lane, under the owner's delegation, after the Java, C++ and Rust ports of `micro.book.rebuild` and `exec.sim.lit.run` were merged onto the Python engine. Separate file so it merges without conflict; numbering continues after HR-56 (branch `stage-h`, `stage-h-rulings-h21.md`). Covers `09-microstructure/order-book.md` and `10-execution/lit-matching.md`. Append-only.

Why: the four languages disagreed on very large decimals. Python's `Decimal` had no range limit but silently rounded products at its default 28 digits; C++ refused input strings above 30 significant digits or 18 decimals with `E_DOMAIN`, and its 128-bit alignment also failed some comparisons and grid checks between in-range values; Rust returned `E_LIMIT` only when a 128-bit coefficient overflowed; Java's `BigDecimal` had no limit at all. So one input could pass in one language, fail in another, and round in a third.

| # | Point | Ruling |
|---|---|---|
| HR-57 | Decimal range | Write a decimal as `c * 10^-s` with `s >= 0` as small as possible (no trailing fraction zeros; an integer keeps its zeros in `c`). It is **in range** when `\|c\| < 10^36` and `s <= 36`. An input decimal string (any price, quantity, `display_qty`, `tick_size`, `lot_size`, fee rate, or book level) must also have `s <= 18`; leading zeros and trailing fraction zeros as written are not counted. Every computed value must be in range too: each sum, difference and product the spec computes (order open quantity, matched rest, iceberg refresh, notional, each fee and fee total, conservation totals, MBP level sums, FOK available quantity, the peg mid sum `bb + ba`, `2 * tick`, the integer tick count of the mid and its price, and a peg's opposite best plus or minus a tick). Reason: 36 digits hold every real price, size and notional with room to spare (Kraken pairs use at most 8 to 10 decimals), and a 128-bit coefficient can honour it exactly: a product of two in-range coefficients that overflows 128 bits is then provably out of range once its factors of ten are cancelled, and the sum of an in-range value and one whose aligned coefficient overflows is at least 1.7e38 at the common scale, so out of range |
| HR-58 | Error and exactness | Outside the range is **`E_LIMIT`** (as `01-core/limits.md`: above a limit), checked after `E_SCHEMA` for the same field; never a rounded, truncated or wrapped value. Inside the range every operation is exact in all four languages: Python computes in a 200-digit context (and the peg mid with an exact `divmod`, not a rounded division); Java uses `BigDecimal` with an explicit check; C++ and Rust use a 128-bit coefficient, cancel factors of ten before a product that would overflow, and do comparisons, grid checks and the peg's integer division by long division, so no in-range pair of values can fail on intermediate width. The error path is not compared (only the code), and the first out-of-range value ends the run, so the four languages agree on whether a case fails. Goldens: `ob_h-0016..0018` and `lit_h-0016..0020` (boundary cases, hand, `oracle/python/gen_stage_h_w2.py`) |

Non-finite inputs of the wave 2 operations: ruling F-2a (`stage-f-rulings.md`, owner decision 2026-11-18). A NaN or infinity token in a decimal-string field is `E_SCHEMA` (HR-12), and that case is the E1 golden (`e1_h2-0001..0005`). The router's one Real input, `step`, is `E_DOMAIN` under F-2 (`e1_h2-0006`).
