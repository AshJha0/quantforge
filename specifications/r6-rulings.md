| R6-1.1 | Curve Jacobian, no mask (finding 3) | `risk.curve.jacobian` returns every entry of the central difference quotient; no build sets an entry to 0. Removing the mask was chosen over rejecting non-local methods with `E_INPUT`: the quotient is well defined for every interpolation, and the entries above the diagonal are the information a user of a globally solved curve needs (up to 0.028 bp per bp on the golden SOFR curve under `MONOTONE_CONVEX`). Every bumped curve uses them |
| R6-1.3 | Jacobian acceptance | The output is the difference quotient at `bump_bp`, as the spec has always defined it, not the derivative. For the smooth methods (`LOG_LINEAR_DF`, `LINEAR_ZERO`, `TENSION_SPLINE`) the oracle asserts every golden entry within 1e-9 absolute plus 1e-7 relative of a Richardson extrapolation at `h`, `h/2` (the plan 14.1 acceptance). For `MONOTONE_CONVEX`, `MONOTONIC_LOG_CUBIC` and `HYBRID`, the curve is piecewise in its data (Hagan-West regions, the Hyman filter; ruling F-40), the derivative itself jumps near some quotes, and the 1 bp quotient differs from the Richardson value by up to 1.4e-3 (diagnosed 2026-11-12, column 10 of the SOFR monotone convex curve). For these the gap is recorded per case in `verified_by`, not asserted to 1e-9: **the plan acceptance is met for three of the six methods and reported as not met, with the reason, for the other three.** Case tolerance: 1e-8 absolute plus 1e-6 relative (two curve solves to 1e-13 over a 2 bp step) |
| R6-3.1 | Expected shortfall (finding 11) | Adopt the cited Acerbi-Tasche estimator with a fractional tail weight (amends F-31; VaR is unchanged). `w = n - n c` (binary64: the F-31 product, then one subtraction), `m = floor(w)`; `es = (sum of the m largest losses + (w - m) L_(n-m)) / w`; `w = 0` gives the largest loss; `tail_count = ceil(w)` (1 when `w = 0`). Applies to `risk.var.historical`, `risk.var.filtered_historical`, `risk.var.monte_carlo`. Chosen over renaming because the operation is called expected shortfall in every user-facing page and the citation is the standard estimator. Outside check: an independent numpy implementation written from the paper's form with `n alpha` (`oracle/python/outside_f.py` `h_hist`), 20 of 20 historical cases agree within 1e-9 relative, at integer (`n = 500`, 99%: `w = 5`) and non-integer (`n = 250`, 99%: `w = 2.5`) tail sizes |
| R6-4.1 | FRTB total (finding 12) | New operation `risk.frtb.sbm_total` (MAR21.7): per scenario, the sum of every class's delta, vega and curvature charge; capital is the largest scenario total, ties to the first of `high`, `medium`, `low`. Each class operation's own `capital` stays as it is (the class's worst scenario) and its text now says it is not the total. The default risk charge, the residual risk add-on and CSR securitisations are not built; README, ROADMAP and the model inventory must say so (docs lane) |
| R6-8.1 | Non-finite results (finding 15) | One code for every operation: a NaN or infinite result or intermediate from finite inputs is `E_NON_FINITE` (the existing contract code), never a crash and never `E_DOMAIN`. The plan text said `E_DOMAIN`; the contract already defines `E_NON_FINITE` for exactly this, and Python, Rust and C++ return it on the fuzz input today, so the plan wording is corrected, not the contract. `E_DOMAIN` stays for non-finite *inputs* (F-2). Java: `Bonds.java:262` must return `E_NON_FINITE` (the Java lane's phase 0 returns `E_DOMAIN`; change it) |
| R6-10.1 | Per-unit tolerances (finding 14) | A per-unit output (rate, spread, volatility, ratio, per-unit factor; list in `tools/check_tolerance_units.py`) never carries an absolute tolerance above 1e-8 unless the case's `tolerance_limit.per_unit_ruling` names an R6-10 ruling. Gated by `python tools/check_tolerance_units.py` (red on a planted case: `--self-test`) |
| R6-10.2 | Re-judging | The gate flagged 460 outputs in 236 cases (my count; the review's "102" used a narrower key set and is not reproduced exactly). Each was run on the v0.8.0 Python, Rust and C++ builds (`conformance/tolerances/R6_REJUDGE_{python,rust,cpp}.json`): every one is within 1e-10 absolute plus 1e-8 relative, worst relative 7e-10. All moved to the new class `per_unit` by `conformance/tolerances/apply_r6_per_unit.py` (rerun after any generator rewrites a golden file). No failure was found, so no formula changed |

| R6-5.3 | G-10c registered (2026-11-12, before its first run) | **Question:** at equal paths (`n = 60,000`), with each method at its own best width, does the smoothed pathwise delta have lower mean squared error than the central bump? G-10b is reworded as "a small bump is noisy": it compared variances at a bump 10 times narrower than the smoothing, so it passed by construction. **Setup:** G-10 digital (`S = K = 100`, `T = 1`, `r = 0.03`, `v = 0.2`), `core.rng` seed 20261110. Widths: smoothing half-width `eps` in {0.1, 0.2, 0.5, 1, 2, 5, 10}; relative bump `h` in {0.0005, 0.001, 0.002, 0.005, 0.01, 0.02, 0.05}. **Pilot** (streams 2 and 3): MSE = exact bias squared (closed form, quadrature) + sample variance / n; best width per method. **Final** (fresh streams 4 and 5): MSE of each method at its best width; ratio pathwise / bump with a 95% interval from the variance terms (`se(ln s^2) = sqrt((k - 1)/n)`, biases exact). **Outcome:** "smoothed lower" if the interval is below 1, "bump lower" if above 1, else "inconclusive"; recorded whichever way it falls (`oracle/G10C_RESULT.json`, `oracle/python/run_g10c.py`) |
