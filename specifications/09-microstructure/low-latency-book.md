# Low-latency order book: complexity, harness and thresholds

Spec version 0.1.0 (stage H wave 1b; confirmed 2026-11-18 by the stage H coordinator). Status: implemented in C++, Rust and Java (H-9, 2026-11-18); a performance structure checked for equivalence against the reference book, with no CLI operation of its own. Rulings HR-18 to HR-24 (`stage-h-rulings-w1b.md`). Plan item 14.7 **H-9** (owner 2026-11-17), quoted:

> Targets written before measuring (R1 rule), per language, on the Actions Linux runner and a pinned local Linux run: (a) per-message book update (add, modify, delete, trade) p50 and p99 and p99.9 latency on a replayed recorded Kraken day at 100 levels and on a synthetic stress stream (bursts, deep sweeps), measured in-process with no I/O; (b) C++ and Rust hot path allocation-free after warm-up (heap allocation counted by an instrumented allocator: 0 in steady state); Java with no allocation in steady state measured by JFR or GC logs, or the miss stated; Python is reference only, no latency target; (c) best bid/ask, depth-at-price and top-N snapshot queries O(1) or O(N) with measured latency; (d) the H-2 correctness check (book equals the venue snapshot at every checkpoint) holds on the same replay, so speed never trades against correctness; (e) regression thresholds in CI as for R4 (H-5): a later PR that worsens p99 beyond the threshold fails; (f) results published with machine, compiler and flags; claims limited to "in-process, simulated feed"; no network or venue latency is claimed

This spec fixes what is required of the data structure, how it is measured and how targets and thresholds are written. It does not choose the implementation. Every answer must equal `micro.book.rebuild` (`order-book.md`) on the same stream; this is the same operation built for speed, not a second definition.

## Operations measured

| Op | Meaning | Required complexity (N = depth per side = 100, L = levels in the message) |
|---|---|---|
| `apply` add/modify/delete | one message, all its levels, truncation, crossed check | O(L log N) worst; O(L) expected when the price is within a bounded tick distance of the touch (HR-19) |
| `apply` trade | a trade row (Kraken book updates already carry the depletion; the trade does not change the MBP book) | O(1): recorded for the per-message distribution, counted separately |
| `best_bid`, `best_ask` | top of book | O(1) |
| `qty_at(price)` | depth at a price | O(1) expected (direct index or hash), O(log N) allowed with the reason stated |
| `top(n)` | the best n levels, written into a caller-supplied buffer | O(n) |
| `checksum` | [KR-CRC] top-10 CRC32 | O(1) in N (fixed 10 levels); allocation-free with a caller buffer |

"Trade" in H-9(a) is a trade row in the replay. For the simulated venues (`10-execution/lit-matching.md`) it is a match that removes queue quantity, and the same table applies to the MBO book there.

## Workloads (fixed here, before any run)

1. **R (recorded replay).** One full UTC day per symbol (BTC/USD, ETH/USD) at 100 levels, as the form B snapshot-differenced stream of `order-book.md` (raw recording is off, HR-11), labelled "snapshot-differenced stream; not the venue's message sequence". The day is the first complete UTC day at 100 levels (24 hours, no gap row), so 2026-11-18 at the earliest, fixed by its file hashes before any timing. Because form B collapses many venue messages into one per second, R understates the message rate and the burst structure; workload S carries the stress. The 14-minute raw sample (2026-11-17 20:29 to 20:43 UTC) is also replayed and reported as "R-raw demonstration, 14 minutes", never as the R result. If raw recording is re-enabled on a larger drive, R moves to a complete raw day.
2. **S (synthetic stress).** Generated by `core.rng` seed 20261117, written once to a file whose hash is recorded: 10,000,000 messages; 100-level book on a 0.1 tick grid; message mix 60% modify, 20% add, 15% delete, 5% trades; bursts of 1,000 messages with 50% of them inside 3 ticks of the touch; every 10,000 messages a deep sweep removing 1 to 100 levels on one side then refilling; 1% of messages touch a price that has just been truncated.
3. Both streams are pre-decoded into a flat in-memory array of fixed-size binary messages before timing (prices as integer ticks, quantities as integer lots scaled by `qty_decimals`, HR-20). Parsing is not timed; H-9(a) says "no I/O".

## Harness

- One process per language, one thread, pinned to one core (`taskset -c 2` on the local Linux run; the Actions runner is unpinned and labelled so).
- Warm-up: the first 1,000,000 messages of the stream (S), or the first hour (R), are applied unmeasured; then the allocation counter is reset.
- Timing: per message, a monotonic clock read before and after `apply` (`clock_gettime(CLOCK_MONOTONIC)` / `Instant` / `System.nanoTime` / `time.perf_counter_ns`). The clock's own cost is measured on an empty loop (1,000,000 pairs) and published; it is **not** subtracted. If the clock overhead p50 is more than half the measured p50, the run also reports batch timing (1,000 messages per sample, divided) and says which is the headline.
- Recording: an HdrHistogram (or a port with the same bucket rule: 3 significant digits, 1 ns to 10 s) per op kind. Replay is as fast as possible (no wall-clock pacing), so there is no expected interval and no coordinated-omission correction; the report says so ([HDR] applies only to paced runs).
- Reported per op kind and overall: count, min, p50, p90, p99, p99.9, p99.99 (only if the count is at least 1,000,000), max, mean.
- Repeats: 5 runs; the reported figure is the median over runs of each percentile, with the min-max range.
- Queries: after each 1,000th message, `best_bid`, `best_ask`, `qty_at` at a random present and a random absent price, `top(10)` and `top(100)`, each timed in the same way.
- Correctness in the same run (H-9(d)): on R, every snapshot row reached exactly by the differenced stream and its checksum recomputed (form B); on the raw demonstration, every form A checkpoint of `order-book.md`; compared, outside the timed region; a single mismatch fails the run whatever the latency.

### Allocation (H-9(b))
- C++: a counting global `operator new`/`delete` (and `malloc` interposition on Linux) in the bench binary; count after warm-up must be 0 over the measured messages.
- Rust: a `#[global_allocator]` wrapper counting allocations; same rule.
- Java: JFR with `jdk.ObjectAllocationSample` and GC logs (`-Xlog:gc`); pass when the measured region shows no GC and an allocation-sample total of 0 for the book's classes; if not achieved, the miss is published with the bytes per message.
- Python: reported (`tracemalloc` peak), no target.

## Targets and thresholds (process; the numbers are in `low-latency-targets.md`)

1. Before any H-9 timing is run, a commit to `benchmarks/targets.md` adds rows L1 to L6 (per language, per workload R and S: update p50, p99, p99.9; query `top(100)` p99; allocation count) with a one-line reason each, the way T1 to T5 were written. The commit hash is quoted in the results.
2. The first measurement is published as it is, met or missed. A target changes only in its own later commit with a reason and before the next measurement ([TGT]).
3. CI regression threshold (H-9(e), as H-5): after the first runner baseline, take 10 runner runs of workload S on `main`; threshold for p99 = max(20%, 3 x the coefficient of variation of p99 across those runs), stated with the runs' raw values ([PERF]: justified by baseline variance). A PR whose median p99 over 3 runs exceeds the baseline by more than the threshold fails. The allocation count gate is exact (0) for C++ and Rust.
4. The baseline is refreshed only by a commit that says why (compiler upgrade, runner image change), never by the PR that regresses.

## Reporting (H-9(f))
Machine (CPU model, cores, frequency governor, RAM), OS and kernel, compiler or runtime and version, flags (for example `-O3 -march=x86-64-v3`, `--release` with `lto`, JVM flags), commit, workload file hashes, warm-up, repeats, clock overhead. Every table carries "in-process, simulated feed; no network or venue latency" and, for R, "crypto venue; not equities or rates" and "snapshot-differenced stream".

## Limit cases
- An update to a price beyond depth 100 on the far side of the book: insert then truncate (it falls off); must cost no allocation.
- Price far from the touch (outside any tick window used for O(1) indexing): must still be correct; the slower path is counted and its share published.
- A sweep emptying a side: `best_*` returns an empty marker, not an error.
- Fixed-point range (HR-20, HR-58): the fast book holds prices in ticks and quantities in lots as signed 64-bit integers. A price or quantity that is inside the exact decimal range of `order-book.md` (36 digits, at most 18 decimals) but whose scaled value exceeds 2^63 - 1 is rejected by the decoder with `E_LIMIT` (above a limit, HR-58), never rounded, truncated or wrapped. This is the fast book's one stated difference from `micro.book.rebuild`: golden ob_h-0016 (36 digits at 18 decimals) is `ok` for the rebuild and `E_LIMIT` for the fast book, and the equivalence tests assert exactly that.

## Golden plan
No numeric goldens (timings are not goldens). Correctness reuses `ob_h-*` and adds a property test: for 1,000 seeded random streams of 10,000 messages, the fast book's `top(100)` after every message equals `micro.book.rebuild` (Python reference) exactly.

## Limitations
In-process only. No kernel bypass, no network stack, no venue round trip. The R replay is differenced from once-a-second snapshots, so it understates the real message rate; only the 14-minute raw sample is a real message sequence, and that only as one public subscriber at depth 100 received it. Shared Actions runners are noisy; their figures are sanity checks and CI gates, the pinned local run is the headline.
