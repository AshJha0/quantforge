| KR-265 | The bump reference and the acceptance | **Plain idea.** The plan asks that AAD equal bump-and-revalue to 1e-8 relative. A binary64 central bump is itself inexact: its rounding error is about `eps |f| / (h |x|)`, which for a small profile point (`ee_i = 1e-3` beside a CVA of 3, `h = 1e-4` relative) is about 3e-9 absolute against a derivative of 6e-3, a relative error near 1e-6. Such a bump cannot judge AAD at 1e-8. So the reference is the bump in 50-digit arithmetic. **Rule.** For each input `x` the reference is `(4 D(d/2) - D(d)) / 3` with `D(d) = (f(x + d) - f(x - d)) / (2 d)`, `d = 1e-12 max(1, |x|)`, `f` the G-41 formulas evaluated at 50 significant digits on the binary64 inputs, with the overlap branch of KR-264 held fixed. The functions are linear or exponential in each input, so the Richardson truncation is of order `d^4` times a bounded fifth derivative (below 1e-45 of the scale) and the rounding about `1e-50 |f| / d` (below 1e-37 of the scale): exact far below 1e-8. The oracle also evaluates the hand-derived closed-form adjoint at 50 digits and refuses to write a golden unless every entry agrees with the bump to 1e-30 of `max(1, |entry|)` (measured: all 13 value goldens agree). **Acceptance.** (A1, every build, every gradient entry of every value golden) `|AAD - ref| <= 1e-12 + 1e-10 max(|AAD|, |ref|)`, the golden's own tolerance (`tolerance_limit`, class `aad_sensitivity`). This implies the plan's bound in the form `|AAD - ref| <= 1e-8 max(1, |ref|)`, since `1e-12 + 1e-10 m <= 1e-8 max(1, m)` for every `m >= 0`. (A2, Python) the same bound on 1,000 seeded random requests (seed 20261120, 1 to 6 buckets, both overlap settings, optional `im` and `capital`), reference computed in the test with Python's `decimal` at 50 digits by the same rule. (A3, Python, reported not gated) the KR-161 binary64 Richardson bump (`h = 1e-4` relative) on the value goldens, with the largest gap recorded in the spec. KR-161's binary64 reference is kept for the operations whose 50-digit forward is not written (the other K-8b operations); for this operation it is replaced, because its own error can exceed the bound it judges. |

| KR-350 | How the G-41 bucket default probability is evaluated (pre-tag audit PT-6) | Plain idea: `S(t_(i-1)) - S(t_i)` subtracts two numbers close to 1 when `h dt` is small, so at `h = 1e-9` about nine of the sixteen digits cancel; the audit measured the builds up to 2.7e-7 relative apart on CVA (read: `STAGE_K_PRETAG_AUDIT_2026-11-22.md`, PT-6). Formal statement: every build evaluates `b_i = S(t_(i-1)) (1 - e^(-h dt_i))` with `1 - e^(-x)` computed as `-expm1(-x)` and `dt_i = t_i - t_(i-1)` computed directly, in `xva.adjustments.value` (both names) and in the forward tape of `xva.sens.aad`; the flat-hazard adjoint of `b_i` is `-(t_(i-1) b_i - dt_i S(t_i))`, the same quantity as `t_i S(t_i) - t_(i-1) S(t_(i-1))` in exact arithmetic without its subtraction. The formulas of G-41 and KR-264 are unchanged in exact arithmetic; at `h = 0` `b_i` stays exactly 0. Worked example: `h = 1e-9`, bucket `(0.5, 1.0]`: the exact value is `(1 - 5e-10 + ...) * 4.99999999875e-10 = 4.9999999975e-10` (to 11 digits); the difference of two binary64 numbers near 1 carries an absolute error up to about 1.1e-16, which is about 2e-7 relative to that (inferred from the ulp of 1; the audit measured up to 2.7e-7 on CVA), while the `expm1` form is correct to a few ulps. Evidence (measured, local laptop, not the acceptance machine): goldens `g41tiny_k-0001` to `-0004` (mpmath at 50 digits, tolerance 1e-13 relative committed before the values) pass, and every existing `xvaadj_g`, `e1g_xva` and `aadadj_k` case passes at its committed tolerance with no expected value changed. |
