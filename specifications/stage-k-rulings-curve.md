| # | Point | Ruling |

| KR-203 | Dates in strict order (amends KR-96 and KR-104; audit KA-C9, Critical) | The fault: the writer retried an unsettled date on every run and also went on to later dates, while the verifier refused a row dated before the last one (`ORDER`). Once an unsettled date had a later row behind it, every run was refused, the gap row included, for good. The rule now: a run handles due dates oldest first and stops at the first one it cannot settle. So at most one date is unsettled, it is the last date with a row, and no later date has a row before it is settled. A date is settled by a DAY row `ok`, `fit_failed` or `holdout_blocked`, or by a GAP row. A GAP row carries `cause`: `late_window` (the late window of KR-96 closed), or `not_published` (the Treasury file, or at a year end the next year's file, holds a later date and not this one; the row carries that file's URL, SHA-256, size and latest date, so the date is closed at once and does not hold up the days after it). Verifier reasons: `ORDER` (a row for another date while one is unsettled, or a date before the last settled one), `DUP`, `MISSING` (the next date is not the next business day), `TS` (a row timed before the row above it), `START` (the first dated row is a DAY row of the run that wrote GENESIS, for the latest day due at that time), `GAPRULE` (a gap without its cause or its evidence). A run whose clock is before the last row refuses and writes nothing. Shown: the audited sequence as a failing test before the fix (commit bb9bce54), and 10,000 generated run sequences, each verified after every run (`python/tests/test_daily_jobs_properties.py`) |
| KR-204 | A download that is not the file (amends KR-91 and KR-99; audit KA-C10) | Bytes that are not the Treasury CSV (no `Date` column, a date that does not read, not UTF-8, empty) are a `fetch_failed` row with code `E_NOT_THE_FILE` and the hash and size of what was received, and the date is retried. `fit_failed` settles a date only for a row dated D with a missing or unreadable cell (`E_MISSING_TENOR`, `E_PARSE`), a CLI error code, or a non-finite result (`E_NONFINITE`; before this ruling that was a refusal, which would have repeated on every run) |
| KR-207 | Rebuild tolerance (amends KR-105; audit KA-C14) | `rebuild` compares `tau`, `taus_ok`, `max_at`, `within_fit_flag`, `operation` and `weighting` exactly, and every number within 1e-6 relative to max(1, value); it reports `exact` true or false. Reason: fit values are written at full binary64 precision and pass through `exp`, `log` and a least-squares solve, so a refit on another platform or library build may differ in the last bits. The chain does not depend on this: `DIAG` and `VERDICT` recompute from the stored strings with correctly rounded operations (sum, square root) |
| KR-209 | What both daily jobs publish (amends KR-90 with KR-109; covers KR-72 and KR-108 of the paper ledger; audit KA-C11) | One position for both jobs. (1) Neither job stores, commits or uploads a source file or a source row. (2) Both publish values from which US Treasury daily par yields can be read. The paper ledger writes five (3 month, 2, 5, 10 and 30 year) in each DAY row. The curve run writes `errors_bp` beside `betas` and `tau`: repricing the thirteen par bonds on those parameters and taking off the errors gives back the thirteen par yields it used, to the last digit. Its rows therefore disclose thirteen, not none. KR-90's "rows hold only fitted parameters ... no source row", and the spec's "this job publishes less than" the recorder, were wrong on this point and are withdrawn. (3) The basis is the recorder's rule and its reading of this source: `docs/developer-guides/recorder-actions.md` (rows carry "for public-domain sources only, the parsed values") and `tools/recorder/sources.json`, entry `us-treasury-par-yields` ("US federal government work (17 USC 105)", `redistribute_raw` "believed yes, unconfirmed", Treasury's own terms not found). Read 2026-11-19 on `origin/forward-log`: the recorder publishes parsed values of three Treasury series on that reading (five par yields, three bill rates, two real yields). The precedent is the reading of the source, and the source file is the same one here; the precedent's own rows hold five par tenors, not thirteen, and the reading is unconfirmed. Both specs say so. (4) Fed GSW: a CONSISTENCY row holds `diffs_bp` beside the DAY row's `zeros_pct`, from which the Fed `SVENY` values compared (up to thirty) follow. The Board's disclaimer, read 2026-11-19 by the curve lane, puts the Board's material in the public domain unless otherwise indicated and asks to be cited as the source; the citation is in every CONSISTENCY row (`gsw.attribution`), in the GENESIS row and in the branch README. (5) The Treasury citation is in every row that used Treasury data, in the GENESIS row and in both branch READMEs. (6) If the recorder's reading of the Treasury source changes, both ledgers stop publishing recoverable values under new format strings (KR-80, KR-102); version 1 rows already published are not rewritten. This is a reading of published terms, not legal advice |

| # | Point | Ruling |
|---|---|---|
| KR-254 | The first dated row (amends KR-203; audit KF-8) | The fault (measured): a first run at 22:50 UTC on D+1, ten minutes before D+1 was due, with the Treasury file holding D+1 and not D (D = 2027-12-06), wrote GENESIS then a `not_published` GAP for D, which the verifier refused (`START`). The rule kept: `START` is unchanged; the first dated row is a DAY row of the run that wrote GENESIS, for the latest day due then. The writer now agrees with it through KR-255: a `not_published` gap needs an earlier run's sighting, so a first run writes a `stale_input` row, never a gap. Chosen over letting `START` accept a gap because the first row then always records what the first run read. Shown: `test_first_run_with_the_date_missing_and_a_later_date_present_verifies` (failed before the fix), and the property test's world now publishes some dates before their 23:00 due time, with first runs at 20:xx and 22:xx; on the unfixed writer its 10,000 sequences give 4 `START` failures, on the fixed one none (measured 2026-11-20, local laptop, not the acceptance machine) |
| KR-255 | A skipped date is closed on a second look (amends KR-203; audit KF-9) | A date missing from a file whose latest date is later is not closed on one download. The first run that sees this writes a DAY `stale_input` row with that file (`latest_date` after the date) and stops. A run at a later instant (a rerun at the same instant is not a second look) that sees a later file again writes the `not_published` GAP. The verifier's `GAPRULE` asks for such a sighting row of the same date, timed strictly before the gap; `STALE` asks only that a `stale_input` row's file has no row for its date. Reason (inferred): a cached or partly updated file, or a year end with the new year's file ahead of the old one, can lack a row that is published later; two downloads at different instants make that less likely, at the cost of at most one run of delay for the days after it. Chosen over "the file also holds the previous settled date", which a partly updated file can pass. Shown: `test_a_not_published_gap_needs_an_earlier_run_that_saw_it` (two planted faults: a sighting whose file was not later, and a gap in the same run as its sighting), the updated KR-203 tests, and the property test's invariant that a `stale_input` row of a date with a later published date carries a later file |
