# Known issues: open audit findings

This page lists every open Critical or Major finding of the different-model AI audits of stage K round 1 (three audits, 2026-11-19, each by an AI model that did not write the audited work, not by a person; plan rule 14.10-5). It is the register that the spec "Limits" sections point to. Since 2026-11-20 it also lists every recorded miss, every move of a plan item to a later point release and the v1.0.0 release-evidence items not yet met ("Recorded misses, moves to a later release and release gaps" below; plan 14.8 K-7). Older known issues are in the [README](../README.md#known-issues). The [results page](results.md) shows these rows beside every stage's test counts, and the [runbooks](runbooks/README.md) say what to do when a daily job, the mutation gate or the release goes wrong.

**State of the code (2026-11-21).** Stage K round 1, the round 2 fixes and the parts merged through `k-v1` (wave 2 capital operations, K-3 adapters, K-5 snapshots, K-6 soak harness, K-7 release evidence) are merged to main by 2026-11-20 (pull requests #58 to #64, read with `gh pr list --state merged`), not tagged; the build version string on main reads 0.10.1 until the v1.0.0 bump; they are released with v1.0.0 (owner decision 2026-11-20: no v0.10.1 tag; the last tag is v0.10.0). The different-model audits A, B, C and the follow-up are answered; what stays open is listed below. Evidence class of every row: measured or read by the auditor, as stated in the audit; rows marked "re-measured" were also checked by the project. Rows are closed by the coordinator, a project lane; the "Re-verified by" column says whether anyone re-checked a closure afterwards (a project lane or a different-model auditor lane, with the date), and says "not recorded" where no re-check is on record (K-9 review finding 17).

**K-2 at v1.0.0 (owner decision 2026-11-20).** The K-2 gate needs 20 recorded trading days in the daily paper ledger. v1.0.0 does not wait for them, and the threshold is not changed. At the tag, K-2 is stated as "not met: N of 20 recorded trading days", with N counted by the ledger verifier (`tools/paper_daily/verify_ledger.py ... --require-days 20`, full command in `docs/developer-guides/paper-ledger.md`) on the ledger at the tagged commit. N was 0 on 2026-11-20 at 13:00 UTC: the schedule is on main since 2026-11-20 (pull request #59) and no scheduled run had happened yet (read from the workflow run list). The first row came later: on 2026-11-21 the `paper-ledger` branch holds one row, for 2026-11-20, which the runner labelled on time (`ledger/summary.json`: `declared_on_time_days` 1, `gaps` 0, read 2026-11-21). That is the runner's own label; the K-2 count is the verifier's, from Bitcoin block times. Measured 2026-11-21 by the coordinator: `verify_ledger.py verify` with the block headers of heights 976796 and 976809 and `--require-days 20` gave "1 recorded trading days, 20 required" (reason DAYS, none unproven), so K-2 is "not met: 1 of 20 recorded trading days (measured 2026-11-21, verifier with Bitcoin headers)"; N at the tag is counted again on the tagged commit.

**Red scheduled workflows.** `tools/check_scheduled_runs.py` (in `repo-gates`) reads the last completed scheduled or manual run on main of every scheduled workflow through the GitHub API and fails while a red one has no open row here naming its file (rows K9-1a to K9-1c below). Plain reading: each row says what is wrong in one sentence, with the size where one was measured. "Answered on branch X, merge pending" means a fix exists with tests but is not yet on the integration branch; the row closes when it is merged and its rulings are confirmed.
