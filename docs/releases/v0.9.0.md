# v0.9.0 release notes: stage J, research and backtesting

Released 2026-11-16 (PR #41; the owner merges and tags). Stage J is done: wave 1 and wave 2 came in PR #40 (no tag), and this release adds wave 3, the financing term structure and liquidity curve, the mutation work, the audit fixes and the docs. CLI contract 1.15.0. Language facts below were checked on the merged tree on one Windows machine with WSL (observed, local); CI results are in the PR.

### Who should read what

- **Using the library** (students, desk quants): "What this release is", "Headline figures", "Added". Each new operation has a spec page, a tutorial and a COOKBOOK recipe.
- **Judging the evidence** (reviewers, research leads): "Research results", "Fixed" and "Honest limits". Each result says how it was checked: *observed* (run on our machine), *outside library* (a separate open-source library gives the same number), *reference-computed* (our own high-precision recomputation, not independent), *self-assessed* (our own reading, no second party).

## What this release is

Plain idea: QuantForge can now tell you whether a research result deserves trust before you spend money on it. It backtests with costs and a lag, purges leaks out of cross-validation, says how much of a Sharpe ratio is luck, builds and stresses portfolios, replays named historical rate shocks, scores an interpolation method on strikes it has not seen, and watches for drift. All of it runs the same way in Python, Rust, Java and C++, and the four builds must agree to stated tolerances on every golden case.

## Fixed

### Model fixes found in the final integration pass (rulings in `specifications/stage-j-rulings.md`)

- **J-I.1, hedge QP rank cut (Python).** The bounded and costed active-set steps of `hedge.qp.solve` cut singular values of the unscaled reduced matrix, so a column small in the caller's units (1e-7) was dropped and the hedge stayed at 0 (objective 1, true optimum x1 = -1e7). The cut is now taken on the Jacobi-scaled matrix, as R6-6.2 requires. Java, C++ and Rust were already right. 4 value cases (`hedgecut_j`, exact KKT enumeration oracle); no existing golden changed.
- **J-I.2, sign state against an equality (Rust).** The costed solver zeroed a coordinate by the R6-6.1 kink tolerance even when an equality forced it nonzero; it now releases that coordinate to the split sign when the zero orthant is infeasible. Python, Java and C++ were exact. 2 value cases (`hedgesign_j`).
- **J-I.3, selection refuses cost and margin inputs (all four, amends I-33).** `hedge.select.solve` silently ignored `half_spreads`, `impact`, `cost_weight`, `margin_rates` and `margin_limit`; any of them is now `E_INPUT`, and the Rust and C++ library entry points refuse them too. 3 error cases (`selectcost_j`).
- **J-I.4, constant series in `hedge.minvar.ratio` (all four, clarifies I-8).** A constant series has sample variance exactly 0, so the operation returns `E_SINGULAR` or `E_DOMAIN`; all four builds had returned a hedge ratio built from rounding error. 3 error cases (`minvarconst_j`).
- **J-W3-17, `risk.backtest.traffic_light` cap.** `observations` above 1,000,000 is `E_LIMIT` in every build (found by fuzzing); Rust now also rejects `exceptions > observations`. 4 error cases (`fuzzfix_j-0040` to `-0043`).
- **KS beyond 128 bits (Rust, C++).** The fallback summed `1 - stay`, which cancelled very small p-values to 0; it now sums exit mass. New golden `drift_j-0036` (n = m = 250, p about 4e-16, relative limit 1e-9); J-W3-13 wording narrowed.
- **Java KS rounding.** The KS ratio is now exactly rounded, so Java agrees with the other builds at the last digit.
- **`hedge_cross` property test.** `correlation01` of a long exchange option is negative in exact arithmetic but `-0.0` once `phi(d1)` underflows (|d1| above about 38.6); the property now allows 0 there, stays strict below 37, and the failing case is pinned. Code unchanged.

- **Degenerate feasible hedge QPs (all four builds, found by the kill round).** `hedge.qp.solve` failed on three valid problems whose feasible set is degenerate, so more constraints are active than the dimension allows:
  1. equalities -x0 + x2 = -2, -x0 - x1 = -1 with x0 >= 1, 0 <= x1 <= 1, -2 <= x2 <= -1 (A = [[1, 0, -1], [-1, 2, -1], [1, 1, 2]], b = (-1, -1, -3)), only point (1, 0, -1), objective 18: Python `E_NO_CONVERGENCE`, Java `E_INFEASIBLE`;
  2. x0 + x1 = 1, margin rates (1, 4), limit 1 (A = I, b = 0), only point (1, 0), objective 1: Python `E_NO_CONVERGENCE`; C++ `E_INFEASIBLE` as found by the kill round;
  3. the costed case (A = [[-1, 1, 2], [-2, -2, -2], [-2, -1, 1], [1, -1, 0]], b = (2, 3, -2, 1), -x0 - x1 + x2 = 1, x1 = 0, half spreads (1, 1, 0), margin rates (1, 2, 0), limit 1), answer x = (-3/38, 0, 35/38), objective 27265/1444: Python `E_NO_CONVERGENCE`.

  Root causes. Python's primal active-set methods put every active bound in the working set; at a degenerate vertex that set is linearly dependent, the least-squares multipliers are not unique and can show a negative sign at the optimum, and dropping that bound gives a zero step that re-adds it, so the loop never settled. A second effect: a step that should be exactly zero carried 1e-17 of rounding, which the ratio test turned into a zero-length block on a dependent bound. Java, C++ and Rust use the Goldfarb-Idnani dual method; its infeasibility certificate (a violated constraint that depends on the active ones with non-positive coefficients) fired on a 1e-16 rounding gap, because the slack test is relative to |d| + |n . y|, which is itself about 1e-16 when the reduced right-hand side cancels to zero.

  Fixes. Python keeps a linearly independent working set [NW06 16.5] (a bound joins only if the working rows keep their rank over the free columns; a tight margin row joins only if independent of the equalities) and steps only in the null space of the working rows. Java, C++ and Rust judge the certificate gap `d_p - sum r_k d_k` against `1e-9` times the rounding scale of the rows it combines (`max(1, |bound| + |x_p,j|)`); below that the constraint is implied to rounding and is skipped until the active set changes. The derivations are in code comments and in `specifications/08-hedging/hedge-solvers.md`. Regression tests in all four languages assert the exact answer and objective for the three cases and for further degenerate cases (an equality that repeats a fixed bound, every bound fixed, a single box vertex with redundant equalities, a margin vertex with spread costs), and that a problem 1e-6 outside each point is still `E_INFEASIBLE`. No golden changed: conformance stays 15,514 of 15,514 in every build.

  Margin start (C++ and Java, found when the C++ fix was first compiled). When the margin binds, C++ and Java found their starting orthant by solving the problem with a heavy margin penalty (1e9 in C++, 1e12 in Java) and refused the problem if that point's margin was above the limit. The penalty point is above the least margin by O(1/penalty), the same size as the 1e-9 tolerance, so C++ refused the "margin tight at its only feasible point" case with a false `E_INFEASIBLE` (Java passed it only because its weight was larger). Both now compute the least-margin point exactly, as Python always did: a linear program in x = u - v with u, v >= 0, each finite bound a row with a slack, solved by a two-phase tableau simplex with Bland's rule (ports of `_simplex` and `_least_margin`, same pivots and tolerances), and refuse only when that margin exceeds `limit (1 + 1e-9) + 1e-12`, the Python test. Rust starts from its non-smooth minimiser and has no penalty step. Checked: C++ sanitizer build, 423 of 423 Catch2 cases; Java `mvn verify` 615 tests and direct least-margin tests mirroring Python's; conformance 15,514 of 15,514 in C++, Java and Rust (observed, 2026-11-17).

## Honest limits

- **Outside checks below the floor for wave 3.** 31 of 56 wave 3 value cases (55.4 %) are checked by an outside library, below the 60 % floor (R6-13). CUSUM, Page-Hinkley and PSI have no free library with our conventions; historical shock is date lookup plus arithmetic. The `interpbt_j` checks rerun the same scipy and numpy calls that made the goldens, so they are not a second independent check. Stage J overall: 130 of 212 value cases (61.3 %, `oracle/OUTSIDE_SHARES.md`); the 20 curves value cases and the 6 hedge fix cases have no outside check. The recount used system numpy 2.4.6 and scipy 1.17.1, not the pinned outside venv.
- **Curves not validated against anyone else.** The financing and liquidity curves are hand and mpmath reference-computed only.
- **The hedge fixes came late.** J-I.1 to J-I.4 were found in the final integration pass, by property tests and review rather than by the golden set; they suggest the hedging operations still have edge cases nobody has tried.
- **One failed result, one narrow pass.** B1 failed; B2 passed on one data set with one method. Neither is evidence about other markets or methods.
- **A3 is a draft.** No drift study has run. The threshold was changed before signing by a delegated decision, not by the owner directly.
- **Mutation scores are partial or lower bounds.** C++ survivors are not all audited; the audit above found many "equivalent" claims false, so treat any remaining equivalence claim as self-assessed. The CI `mutation-report` check now samples 40 mutants per module on pull requests, as the weekly run does; the earlier 12-mutant sample allowed no survivor under the 65% Wilson bound (11/12 gives 0.646), so a module killing 90% failed about 72% of the time, which explains the repeated failures before this release. It is not a required check. Rust `hedge_solvers.rs`: 91.7% on a full run (see the table above and Known issues).
- **Simulated data.** Wave 1 and 2 goldens and the B1 surface are synthetic. Only B2 and the shock library touch real data (US Treasury par yields).
- **Machine scope.** All local runs are on one Windows machine with WSL. Rust and C++ binaries cannot run natively there.
- **No different-model audit** of wave 3; Rust and C++ property tests are limited to the added unit tests.
- **Not done:** the G-42b ORE re-test is a recorded result, not a gate; pa11y runs in CI only; fuzzing has not run on `main` since the 0.8.3 fixes.
