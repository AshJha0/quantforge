# Incremental curve update (stage K)

Every number below is from the Python build in this repository, run on 2026-11-21 through <code>uv run --locked quantforge batch</code> on the golden inputs (measured, local laptop, not the acceptance machine). Inputs are synthetic.</p>

Back to [Curves](README.md).

**Plain idea.** In a sequential bootstrap each pillar is solved from its own quote and the pillars before it. A quote therefore cannot move any pillar before its own maturity. When one quote ticks, the pillars before it can be copied from the last curve and only the rest solved again. The shortcut is only safe if it gives exactly the same bits as a full rebuild, and if it refuses a cached curve that does not belong to the old quotes.

**Formal statement.** `specifications/02-curves/incremental-update.md` 1.1.0 (ruling KR-5; audit rulings KR-230, KR-231, KR-235; read 2026-11-21).

| Operation | Inputs | Outputs |
|---|---|---|
| `curve.bootstrap.par_annual` | `quotes`, 1 to 200 decimals, each above -1 (more than 200 is `E_LIMIT`) | `discount_factors` |
| `curve.incremental.update` | `previous_quotes`, `previous_discount_factors`, `new_quotes` | `discount_factors`, `first_changed_index`, `recomputed` |

Annual par swaps with accrual 1 give `P_k = (1 - S_k sum_{i<k} P_i) / (1 + S_k)`. The arithmetic is fixed by the CLI contract's numeric rules: no fused multiply-add, sums in array order (`acc = 0`; for each quote `P = (1 - S * acc) / (1 + S)` as separate operations, then `acc = acc + P`). `curve.incremental.update` first rebuilds the previous curve from `previous_quotes` and refuses the cache with `E_INPUT` unless it matches bit for bit; then it copies pillars `0 .. j-1`, where `j` is the first index whose quote changed, and solves pillars `j .. n-1` again, so `recomputed = n - j`.

**Worked example.** Quotes 2%, 2.5% and 3% (`inc_k-0001`):

| Pillar | Quote | Discount factor | How |
|---|---|---|---|
| 1 year | 2.0% | 0.9803921568627451 | `1 / 1.02` |
| 2 years | 2.5% | 0.9516977522716404 | `(1 - 0.025 x 0.98039) / 1.025` |
| 3 years | 3.0% | 0.9145993230349208 | `(1 - 0.03 x (0.98039 + 0.95170)) / 1.03` |

Each tick, with the same cached curve:

| Golden | New quotes | `first_changed_index` | `recomputed` | New discount factors |
|---|---|---|---|---|
| `inc_k-0002` | 2%, **2.6%**, 3% | 1 | 2 | 0.9803921568627451, 0.9498146237052325, 0.9146541714397676 |
| `inc_k-0003` | 2%, 2.5%, **3.1%** | 2 | 1 | 0.9803921568627451, 0.9516977522716404, 0.9118382277563861 |
| `inc_k-0004` | unchanged | null | 0 | the cache, unchanged |

Read the second row of the first table against `inc_k-0002`: when the 2-year quote rises, the 2-year discount factor falls (0.95170 to 0.94981), and the 3-year factor rises slightly (0.91460 to 0.91465), because a larger earlier annuity term `sum P_i` is replaced by a smaller one in the 3-year equation. A tick at one tenor moves later pillars in a direction that depends on the curve, not only at the tenor itself.

**What can go wrong, and what the goldens pin.**
- A stale cache. `inc_k-0006` has its last cached factor one unit in the last place above the bootstrap: the answer is `E_INPUT`. Without the check the update would copy a wrong pillar into every later curve.
- Fused multiply-add. `inc_k-0007` and `inc_k-0008` are seeded quote vectors for which a bootstrap computed with fused multiply-add differs in one pillar (KR-235(a)); a build that lets its compiler contract `1 - S * acc` fails them.
- Lengths. Previous and new quotes of different lengths are `E_INPUT` (`inc_k-0005`).

**Evidence.** 10,000 random quote vectors bit-identical to a full rebuild, and on the stage B production bootstrap an incremental path in all four builds patches 10,000 of 10,000 moves bit-identically (keys `incremental_property` and `incremental_property_stage_b_patched`, `program/STAGE_K_W1_HANDOVER.md`; read). Outside share 4 of 6 value cases by blind re-derivation (`oracle/OUTSIDE_SHARES.md`, generated). Capacity: 200 quotes, the documented limit, ran in 0.009 s in Python and 0.008 s in Java, and 201 quotes returned `E_LIMIT` in both (`docs/capacity.md`, local laptop, not the acceptance machine).

**Limits.** Annual accrual and par swaps only; no interpolation between pillars; the operation is stateless, so the caller keeps the cached curve between calls.
