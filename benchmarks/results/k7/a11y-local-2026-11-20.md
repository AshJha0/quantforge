### Tutorials 36 and 39: the cause and the fix (KR-227), 2026-11-21

**Plain idea.** On those two pages pa11y did not find a contrast fault: axe-core's contrast rule crashed. It crashed because of where it looked, not because of a colour.

**Formal statement.** axe-core 4.2.4 (the copy pa11y 6.2.3 runs) places every element on a grid of 200 px cells, with a separate grid for each box that scrolls, and the color-contrast rule first reads the cell under the middle of each text element's bounding box (`lib/commons/dom/get-rect-stack.js` `createGrid` and `getRectStack`, `get-element-stack.js`; read at tag v4.2.4). A grid for a scrolling box holds only the line boxes of the elements inside it. A multi-line inline `<code>` inside a `<pre>` that scrolls sideways has one line box per line; when its long lines are at the top or bottom and its middle lines are short, the middle of its bounding box falls in a cell that no line box touches, the cell is undefined, and `.filter` on it throws. pa11y reports the thrown rule as `color-contrast` with no element (read: the diagnostic step of Docs run 44805977858 printed `incomplete rule error: Cannot read property 'filter' of undefined` for both pages, light and dark).

**Worked example.** Tutorial 36, step 1: the `<code>` box is 1060 x 785 px at (140, 926) on a 1280 x 1024 view, so its middle is at (671, 1319), cell row 6, column 3. The lines in row 6 are short and reach only columns 0 to 2 (measured with a replay of the lookup in the installed Chrome). Tutorial 37 has the same layout but a long line near the middle, so it passes.

| Check (local laptop, not the acceptance machine; Playwright 1.64.1, installed Chrome, 1280 x 1024) | Before the fix (CI-built site of run 44805977858, 836 pages) | After the fix (local build, 861 pages) |
|---|---|---|
| Replay of axe 4.2.4's grid lookup (`tools/check_site_a11y.py --browser`, rule `axe-4.2.4-grid-gap`) | 2 pages per mode: tutorials 36 and 39, the step-1 `<code>`; no other page | 0 pages, light and dark |
| Computed text contrast, AA | not rerun | 0 failing of 161,860 text elements per mode |
| Page width at 1280 px and 375 px light and dark, Mermaid rendered (`tools/check_site_view.py`) | not rerun | 861 of 861 pages pass in all three views |

Evidence class: measured, 2026-11-21; the replay found exactly the two pages CI reported, out of 836. Fix: `tools/build_site.py` CSS `pre code{display:block}`, so the code is one box and its middle lies on its own cells; `tools/test_tools.py` checks the rule. A first try, a block as wide as its longest line (`width:max-content`), failed in CI (Docs run 44920662025, read): on `COOKBOOK.html` the middle of long blocks fell outside the visible part of the `<pre>` and pa11y reported 44 contrast results axe could not measure, so the block now stays as wide as the visible `<pre>`. Nothing is excluded and no rule is turned off. The KR-227 result is the CI run, not this table.

### Docs run 44922499739: tutorials 36 and 39 pass; question bank 14 is a second axe-core 4.2.4 trap, 2026-11-21

**Plain idea.** With the code-block fix, every page passed in both modes except one, `docs/question-bank/14-stage-k-risk-platform.html` (860 of 861 per mode, read from the run's `a11y-summary.md`). That page has no colour fault either: axe gave up on one italic line.

**Formal statement.** The diagnostic step printed `incomplete p:nth-child(465) > em`, "Unable to determine contrast ratio", with no background reason (read). The element is `<p><em>Level: advanced. Evidence: ... Source: <code>specifications/12-platform/lock-free-snapshots.md</code></em></p>`. When an element's own text has at most one line box, axe 4.2.4 takes the stack under the middle of its bounding box (`lib/commons/color/get-rect-stack.js`) and returns no background, with no reason set, if the element is not in that stack (`get-background-stack.js`; read at tag v4.2.4). On the runner the `<em>` wraps onto two lines with all its own text on the first and only the `<code>` path on the second; the middle of its box is then in the gap between its two line boxes (inferred from the source and the replay below; the runner's layout itself was not measured).

**Worked example.** The local fonts keep that line on one row, so the replay does not fire with them. With Verdana forced as a stand-in for the runner's wider fallback font (inferred stand-in), the replay (`--browser`, rule `axe-4.2.4-own-stack-miss`) finds exactly this `<em>`, middle at (638, 30026) outside its own line boxes, and nothing on the other 860 pages (measured, local laptop, not the acceptance machine).

After the fix (local build, 861 pages, measured): the Verdana replay finds 0 pages; with the local fonts the browser pass finds no finding in light and dark (0 contrast failures of 161,865 text elements per mode, no grid gap, no own-stack miss); 861 of 861 pages pass the width check in all three views.

Fix: `tools/build_site.py` `a11y_fix` gives a paragraph that is one `<em>` or `<strong>` the class `para`, and the CSS shows it as a block (the element and its meaning stay); `tools/test_tools.py` checks it and that mixed emphasis is left alone. Nothing is excluded and no rule is turned off. The KR-227 result is the next CI run.
